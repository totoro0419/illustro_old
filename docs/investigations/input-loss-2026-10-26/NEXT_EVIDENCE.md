# 未取得の証拠を取るための最少手順

**この文書は実行結果ではない。ユーザー実機の追加記録は未取得。** 修正や描画停止・高速化の実験は含めない。

## 同じ接触を別の場所で観測する

現在の停止位置は「実際に触れた指」と「ページに保存された開始記録」の間である。次の3点を同じ試行で取る。

1. 指が触れた・離れた時刻とペンの位置が分かる記録。画面録画だけでは指の物理接触やペンの近接は証明できないため、必要なら手元も映す。
2. 端末の全入力機器の生記録と、取得可能ならAndroidからChromeへの配送記録。
3. ページ全体・文書・操作領域に同じ入力が届いたかの記録。本線反映の目印と同じ時計で取る。

端末名・Androidのビルド・Chromeの版・開いたURL・アプリ版を試行と結び付ける。推定値で埋めない。

## ページ側：表示や受付を変更しない記録

[公開診断ページ](https://totoro0419.github.io/illustro/qa/m10-real-input/)から現在のアプリを開く。端末のChromeを[公式のリモート検査](https://developer.chrome.com/docs/devtools/remote-debugging)で調べられる環境なら、その実機ページのConsoleで [capture-dom.js](capture-dom.js) の内容を実行する。別の画面・PCの同名ページで代用しない。

このコードは、画面の要素やスタイルを追加せず、入力の取消しやポインターの捕捉を行わない。既存の受付関数・描画関数も変更しない。通知を受け取ってメモリーに記録するだけである。計測の負荷が症状へ影響したかは別に確認する。

一試行を終えた後、同じConsoleで停止・書き出しを行う。

```js
copy(JSON.stringify(window.__illustroInputLossEvidence.stop(), null, 2))
```

60秒で自動停止する。再計測はページを再読み込みして新しく開始する。`metadata.overwritten` が0か、試行の開始まで記録が残っているか、計測APIが対応しているかも確認する。

同じ通知には共通番号を付ける。ただしこれはWebページ内だけの番号で、Androidのイベント番号とは同一ではない。ペンのホバー通知が記録されなかっただけで「ペンは検知範囲外だった」と認定しない。

## 端末側：取得できる範囲を確認する

すでに検査用接続が利用できる端末で、まず読み取りを試みる。

```sh
adb devices
adb shell getevent -lp
adb shell dumpsys input
```

続いて、対象試行の間だけ全入力機器の生記録を保存する。

```sh
adb shell getevent -lt > illustro-kernel-events.txt
```

試行後にCtrl+Cで停止する。タッチ用機器とペン用機器が別になっている可能性があるため、最初から一つの機器だけに限定しない。指の接触番号とペンの接触・近接の報告を識別する。

[Android公式getevent資料](https://source.android.com/docs/core/interaction/input/getevent)は、これがカーネルからの生入力であり、時刻が `CLOCK_MONOTONIC` であると説明する。権限によって取得できない端末もある。「Permission denied」「機器が見えない」は入力なしとは別の結果として保存する。取得のためのroot化・設定変更・入力注入はこの手順に含めない。

Android側の詳細な配送は、対応していれば `android.input.inputevent` 等の記録を検討できる。ただし、[公式Winscope取得手順](https://source.android.com/docs/core/graphics/winscope/capture/adb)は開発用ビルドを前提とし、[Perfettoの設定](https://perfetto.dev/docs/reference/trace-config-proto)も版・権限・記録規則によって取得範囲が違う。市販端末で生入力からChrome受信まで必ず取得できるとは扱わない。

`dumpsys input` の単発状態だけで、過去の接触を捨てた分岐は確定できない。Chromeへ配送されたイベント、ChromeのJava/nativeで受けたイベント、内部で処分した理由を同じ試行に対応させる。通常のChromeの性能記録に目的のイベントがなかった場合も、非対応と入力未発生を区別する。

## 動作を改造せずに比べる条件

同じ端末・同じアプリ版・同じ入力方法で、各条件を複数回繰り返す。症状が一度消えたことを原因確定にしない。

| 条件 | 固定すること | 比べたいこと |
|---|---|---|
| 太いGペンの後、ペンを近くに保つ／十分離す | 線、指操作、作品、端末 | ペン近接と指欠落の関係 |
| 細い線／太い線の直後に同じ指操作 | ペンの離し方・距離、アプリ版 | 本線の反映時間が変わったとき入力開始も連動するか |
| 線を描かず、ペンが近い／遠い状態で指操作 | 指の場所・動かし方 | 正式描画なしで同種の入力欠落が起こるか |
| 指を置き続ける／一度離して置き直す | ペンの位置と線 | 同じ接触の復帰と、新しい接触の受付を区別する |

ペンの近接、物理接触、本線の表示を記録しない比較では、結果が違っても直接原因まで断定しない。反映の文字だけで実際の描画完了時刻を決めない。

## 時計を対応させる

生入力の秒数とページの `performance.now()` は起点が違う。取得開始時刻の引き算だけで合成しない。同じペンの接触・離筆など、両方にある複数の特徴を対応させ、時刻のずれと誤差を示す。動画にも対応点を設ける。誤差の範囲より小さな前後関係は判定しない。

## 記録がそろったときの判断

| 同じ接触の観測 | 次に特定する場所 |
|---|---|
| 指の接触を確認し、適切な全機器の生記録にも指がない | センサー・制御・ドライバー側。記録の取りこぼしと機器の選び違いを先に除く |
| 生入力はあるが、AndroidがChromeへ配送しない | Android側の具体的な抑制・破棄・待機分岐と条件 |
| Androidの配送とChrome受信はあるが、ページ全体に開始通知がない | Chrome内部の配送・入力処分・イベント生成。分岐理由をさらに取得する |
| ページ全体にあるが操作領域にはない | 入力先、伝播、文書、表示・受付条件 |
| 操作領域にあるが表示変換が始まらない | その試行で選ばれたIllustroの受付条件・操作処理 |
| 途中の記録を取得できない | その境界は未確定。残った候補を正解としない |

停止の瞬間だけでなく復帰の前後も照合する。今回の成果はこの記録の準備までであり、上表を適用できる実機の一式はまだない。
